# 코드 스타일

## 조건문

- if문이 한 줄이여도 중괄호를 작성한다.

```jsx
if (true) {
  return true;
}
```

## export 방식

- Next.js가 강제하는 특수 파일(`page.tsx`, `layout.tsx`, `not-found.tsx` 등)은 `export default`를 사용한다. (프레임워크 요구사항)
- 그 외 컴포넌트/함수는 `named export`를 사용한다.
  - 이유: named export는 import하는 쪽에서 이름을 마음대로 바꿀 수 없어서, 같은 컴포넌트가 파일마다 다른 이름(`Btn`, `MyButton` 등)으로 불리는 것을 막을 수 있다. (default export는 import할 때 이름을 자유롭게 지을 수 있어서 이런 문제가 생기기 쉽다.)
  - 이유: 자동 이름 변경 등 리팩토링 툴 지원이 named export에서 더 잘 동작한다.
- **마이그레이션 정책**: 현재 기존 컴포넌트는 대부분 `export default`로 작성되어 있다. 한 번에 전체를 바꾸지 않고 아래 순서로 점진적으로 전환한다.
  - 새로 작성하는 컴포넌트: `named export`로 작성한다.
  - 기존 컴포넌트: 당장 리뷰 대상은 아니지만, 해당 파일을 수정할 일이 생기면 그 김에 `named export`로 전환한다.

## import 방식

- 같은 feature/컴포넌트 폴더 안(형제 파일, 하위 폴더)을 참조할 때는 상대경로(`./`, `../`)를 사용한다.
- 다른 feature나 최상위 폴더 경계를 넘어갈 때(예: 다른 feature 참조, `components/`, `lib/`, `hooks/` 등 공통 영역 참조)는 `@/` alias(`@/components`, `@/features` 등)를 사용한다.
- import 시 파일 확장자(`.ts`, `.tsx` 등)는 붙이지 않는다.

## Props 타입

- Props 타입은 `interface`를 기본으로 사용한다.
  - union/tuple처럼 `interface`로 표현 못 하는 경우에만 `type`을 사용한다.
  - 기존 `type` 6곳은 강제 일괄 변경하지 않고, 해당 파일을 수정할 때 자연스럽게 전환한다.

## type

- `any`는 사용하지 않는다.
  - 타입을 알 수 없는 경우 `unknown`을 사용하고, 필요한 곳에서 타입 좁히기(type narrowing)를 한다.
